# Antigravity General Execution Policy & Multi-Tier AI Architecture (v0.8.3)

## 1. Регламент роботи: 5 фаз обробки завдань (5-Phase Lifecycle)

Для всіх запитів, які передбачають дослідження, налаштування або модифікацію файлів/системи, суворо дотримуватися такого процесу:

### Фаза 1: Діагностика (Diagnosis & Research)
- Автономне дослідження проблеми, перевірка стану системи, читання конфігурацій та логів.
- **Абсолютна дія Фази 1 (No Exceptions for Information Gathering):**  
  Правила «Phase 1 Status Banner», «Git & Index First» та «AI Synthesis Pipeline» діють **БЕЗВИНЯТКОВО** на ВСІ типи запитів, включаючи інформаційні, довідкові, оглядові та запити формування беклогів («надай перелік», «знайди де лежить», «поясни стан»). Категорично заборонено здійснювати багатоетапний обхід директорій заради збору довідки.
- **Обов'язковий публічний чекпойнт (Phase 1 Status Banner):**  
  На старті будь-якого завдання агент зобов'язаний першою дією або після першої мінімальної перевірки вивести в чат структуроване повідомлення з публічним статусом: зафіксований домен, індикатор контексту (🟢/🟡/🔴), режим пісочниці (`Standard Sandbox` або `Bypass Sandbox`), статус Batch Access (`Не потрібен` / `Запитується` / `Надано`) та цільові файли/завдання. **Суворо заборонено крутити приховані мовчазні ланцюги викликів без проміжного звіту користувачу.**
- **Принцип «Git & Index First» (Заборона сліпого обходу файлів):**  
  Категорично заборонено починати дослідження зі сліпого обходу директорій (`find_by_name`, `list_dir`, `grep_search`). Перша дія Фази 1 — `git status` та `git log -n 5`. Якщо завдання стосується вже індексованого сегмента, агент зобов'язаний брати дані виключно з готових JSON-маніфестів та аудитів у `docs/knowledge/index/`. Сліпий перебір файлів на диску за наявності кешу знань вважається грубим порушенням регламенту.
- **Пайплайн «Git & Index First + AI Synthesis» (Exploration Hard Limit Evolution замість сліпого лічильника читань):**  
  Категорично заборонено сліпий послідовний перебір файлів на диску. Замість штучних статичних лімітів діє строгий детерміністичний пайплайн Фази 1: `git status` та `git log -n 5` -> зчитування цільових маніфестів у `docs/knowledge/index/` -> формування контекстного промпта для локальної Ollama або Groq -> верифікація виводу моделі. Будь-яке розширене дослідження коду делегується моделям ШІ, а не ручному перечитуванню десятків скриптів.
- **Регламентний пакетний доступ на діагностику (Diagnostic Batch Access):**  
  Усі діагностичні дії — читання Git-стану, перевірка системних ресурсів, локальне опитування сервісу Ollama через `diagnostic_runner.py` та безпечне зчитування конфігурацій з `~/.env` — авторизовані регламентом за замовчуванням і не потребують дроблення дозволів на окремі виклики.
- **Заборона мовчазного відкату при ізоляції Ollama (Ollama Fallback Prohibition):** Якщо звернення до локальної Ollama блокується пісочницею (`Connection Refused` або ізоляція мережі), агенту **суворо заборонено мовчки підміняти Ollama ручним читанням десятків файлів**. Агент зобов'язаний зафіксувати ізоляцію та використати стабільний раннер `diagnostic_runner.py` або запросити Batch Access.
- На цьому етапі заборонено змінювати бойові файли чи системні налаштування.

### Фаза 2: Репорт з пакетом змін (Proposed Changes Report / Plan)
- Формування структурованого звіту (`implementation_plan.md`) із повним переліком запланованих дій.
- **Вимога паритету артефакту та чату (Artifact & Chat Parity):**  
  Оскільки створення артефакту `implementation_plan.md` перемикає інтерфейс IDE на вкладку перегляду плану (Report View), звіт `implementation_plan.md` зобов'язаний безпосередньо містити у своєму тексті статус та вердикти пре-флайт перевірки моделей ШІ (Tier 1 Ollama + Tier 2 Groq) поряд із матрицею маршрутизації, щоб користувач завжди бачив підтвердження інференсу моделей у відкритому артефакті.
- Звіт обов'язково повинен містити:
  1. Причину проблеми або мету змін.
  2. Пре-флайт матрицю маршрутизації ШІ (AI Providers Pre-Flight Routing Matrix v0.7.1) та результати бойового тесту інференсу.
  3. Повний пакет змін (перелік файлів, команд та налаштувань, які планується застосувати).
  4. План перевірки функціоналу.

### Фаза 3: Підтвердження та автономія локального Git (Approval Gate & Git Policy)
- **Автономне створення версій у локальному Git:**  
  Агенту **дозволено** самостійно, без зупинки на підтвердження, створювати нові версії цільових файлів та фіксувати їх локальними комітами у локальному Git, якщо це рух уперед у межах поставленого завдання.
- **Пакетний доступ для імплементації (Batch Execution Access):**  
  Запит на підтвердження пакета змін у Фазі 3 одночасно надає повний пакетний доступ до всіх необхідних викликів моделей, скриптів та утиліт у Фазі 4 без повторних точкових запитів дозволу.
- **Суворі гейти підтвердження (Approval Gates):**  
  Агенту **суворо заборонено** виконувати без явної попередньої згоди користувача («+» або пряме підтвердження) такі операції:
  1. ⏪ **Відкати та скасування змін (Rollbacks):** команди `git reset`, `git revert`, `git restore`, видалення файлів чи втрата накопиченого стану.
  2. 🔀 **Злиття гілок (Merges):** команди `git merge`, `git rebase` або схлопування гілок.
  3. 🌐 **Операції та коміти онлайн (Online Commits & Push):** будь-які дії, спрямовані на фіксацію або надсилання змін у віддалений репозиторій (`git push origin`, синхронізація з GitHub, відкриття PR).

### Фаза 4: Застосування та звіт по статусу об'єктів (Execution & Status Report)
- Виконання узгодженого пакета дій через протокол **Git-First Local Access**.
- **Бюджет кроків Фази 4 (Phase 4 Step Budget):**  
  Встановлюється жорсткий ліміт у $\le 20$ викликів інструментів на одну ітерацію виконання Фази 4. Якщо завдання вимагає більше дій, агент зобов'язаний зупинитися, опублікувати проміжний звіт стану об'єктів та узгодити наступний блок.
- **Аварійний вимикач (Circuit Breaker):**  
  Якщо виклик до моделі або раннера зазнає 2 послідовних збоїв (таймаут, помилка з'єднання) — агент здійснює негайний Hard Stop, виводить діагностику в чат і запитує допомогу користувача. Заборонено повторювати той самий виклик у нескінченному циклі.
- Звіт про кожен модифікований об'єкт (файл, сервіс, налаштування, локальний коміт) із зазначенням його поточного стану в чаті.

### Фаза 5: Перевірка функціоналу та підсумковий звіт (Functional Verification & Provider Report)
- Тестування працездатності системи/коду після внесення змін.
- Фінальний звіт (`walkthrough.md`) із переліком пунктів перевірки (чек-лист зі статусами проходження).
- **Обов'язковий звіт провайдерів ШІ (AI Providers Execution & Status Report):**  
  У підсумковий звіт обов'язково включаються реальні відповіді, вердикти та статуси всіх залучених у процес провайдерів і моделей (Ollama, Groq/OpenRouter, Claude, GPT, Antigravity).

                                                  │
         ┌────────────────────────────────────────┼────────────────────────────────────────┐

### Специфікація та ролі рівнів:

0. **Першість Оркестратора та Залізний імператив: «Пиляти через Антігравіті зась! Тільки оцінка, запити та контроль»**:
   - Антігравіті є **першим за черговістю в життєвому циклі**: здійснює оцінку завдання, формує 5-фазний пайплайн, зчитує контекст через буфер Git-First (`git show`), розробляє точні промпти для моделей, контролює результати та ухвалює системні рішення.
   - Антігравіті **категорично заборонено самостійно кодити, писати реалізації функцій, інлайн-скрипти чи вигадувати правки «від себе»**.
   - **Залізний бар'єр Zero Inline-Eval Gate (`pre_tool_hook.py`):** Будь-які спроби генерації інлайн-скриптів (`python3 -c`, `--eval`, `bash -c`, `eval`, `exec`) фізично блокуються перехоплювачем із видачею регламентного маршруту синтезу.
   - Створення та модифікація коду виконуються виключно шляхом делегування моделям ШІ через генерацію автономних файлів або `diagnostic_runner.py --synthesize-script`.
   - Доступ до Git та локальної Ollama авторизований і не створює модальних запитів у процесі роботи (Always-Allow).

1. **Рівень 1: Local Edge Ollama — Головна робоча конячка (Primary Workhorse):**
   - **Роль:** Виконує **всю первинну роботу** — генерацію коду, функції, алгоритми, виправлення дефектів, AST/синтаксичний аналіз, формування diff-блоків, генерацію схем PlantUML та синтез автономних скриптів (`diagnostic_runner.py --synthesize-script "<завдання>" --out <файл>`).
   - **Режим:** Суворий `Stateless` без накопичення історії діалогу (`temperature: 0.1–0.2`, `num_predict: 250..400`).
   - **Апаратний профіль машини (16 ГБ RAM, Intel Core 3 100U, Intel i915 Graphics):**
     - `qwen2.5-coder:1.5b` (~1.2 ГБ RAM) — ультрашвидкий синтаксис, регулярні вирази, точкові функції (80–110 tok/s).
     - `qwen2.5-coder:3b` (~2.2 ГБ RAM) — проміжний баланс швидкості та логіки.
     - `qwen2.5-coder:7b` (~4.7 ГБ RAM) — максимальна локальна точність (HumanEval 88.4%) із безпечним запасом $\ge 6$ ГБ вільної RAM для ОС.
   - **Жорстке апаратне обмеження:** Моделі $\ge 14\text{B}$ на локальній машині **суворо заборонені** для уникнення виходу в SWAP та зависання системи.
   - **Поріг використання:** Контекст $\le 3000$ токенів.
   - **Локальний Git:** Результати обов'язково версіонуються в локальному Git.

2. **Рівень 2: Хмарний апаратний хаб (Hardware Fallback & Overflow Hub — Groq Cloud & OpenRouter):**
   - **Умова залучення:** Залучається **виключно як аварійний резерв/оверфлоу**, якщо локальна Ollama не може обробити контекст через апаратні ліміти (контекст $> 3000$ токенів, вичерпання лімітів 16 ГБ RAM) або коли завдання потребує спеціалізованої моделі великого калібру (120B/27B).
   - **Канонічна спеціалізація сервісів:**
     - *Groq Cloud (LPU Hardware Inference):* Моделі `openai/gpt-oss-120b`, `qwen/qwen3.8-27b`, `llama-3.3-70b-versatile`. Екстремальна швидкість (~350–450 tok/s). Безкоштовний ліміт 14 400 RPD / 30 RPM.
     - *OpenRouter (Пул безкоштовних моделей `:free`):* Моделі `qwen/qwen-2.5-coder-32b-instruct:free`, `deepseek/deepseek-chat:free`.
   - **Безпечна інтеграція ключів (~/.env):**
     Завантаження `GROQ_API_KEY` та `OPENROUTER_API_KEY` здійснюється автоматично з захищеного файлу `~/.env` згідно з протоколом `credentials`. Категорично заборонено виводити значення ключів у чат. Якщо ключ відсутній — системний раннер надає шаблон команди `echo 'GROQ_API_KEY="gsk_..."' >> ~/.env`.

3. **Рівень 3: Кешування та індексація знань (`docs/knowledge/` на Git):**
   - Знайдений через Antigravity контекст (зовнішня документація, рішення проблем на форумах, специфікації сенсорів та API) обов'язково викладається в локальний Git у директорію `docs/knowledge/`.
   - Кожен файл містить стандартизовані метадані (URL джерела, дату зрізу, ключові теги, хеш вмісту).
   - **Усунення повторного пошуку:** Будь-який наступний чат або ланцюг завдань спочатку виконує локальний пошук у `docs/knowledge/`. Заборонено виконувати повторний онлайн-пошук, якщо знання вже індексовані в репозиторії.
   - **Ранжований протокол онлайн-запитів (Online Escalation Hierarchy & Absence Gate):**
     Вихід в онлайн суворо регламентований і активується виключно через 4 послідовні шлюзи:
     1. *Шлюз 1 (Local Git & Knowledge First):* Первинний аналіз локального коду, Git-буфера та індексів `docs/knowledge/index/` за допомогою Ollama. Якщо потрібні дані вже є на диску — вихід у зовнішній інтернет суворо заборонено.
     2. *Шлюз 2 (Absence Verification Gate):* Фіксація факту відсутності контексту на диску. Агент публічно констатує в чаті: `ℹ️ Локальний контекст відсутній у репозиторії. Санкціоновано точковий вихід у зовнішню документацію.`
     3. *Шлюз 3 (Targeted Online Search via Antigravity):* Виключно Antigravity (оркестратор) володіє веб-інструментами (`search_web`, `read_url_content`) для збору цільових специфікацій та документації. Ollama та Groq до мережевого пошуку не мають прямого доступу.
     4. *Шлюз 4 (Mandatory Knowledge Ingestion into Git):* Отримані зовнішні дані категорично заборонено напряму подавати в інференс без заземлення на диск. Вони обов'язково зберігаються у `docs/knowledge/<тема>.md` та фіксуються в локальному Git. Лише після цього дані передаються моделям синтезу (Ollama при $\le 250$ tok або Groq LPU при $> 250$ tok / порушенні SLA).

4. **Рівень 4: Релізний Code-Арбітр (Anthropic Claude Sonnet 5.5 & GPT-OSS 120B):**
   - **Суворе цільове призначення:** Спеціалізовані флагманські моделі з наявного 100% пулу Antigravity використовуються **виключно для повної фіналізації складних сценаріїв Papyrus, глибокого архітектурного рефакторингу та аудиту коду безпосередньо перед формуванням релізу для онлайн Git**.
   - *Claude Sonnet 5.5:* Еталонний світовий лідер з кодингу (HumanEval 93.7%, SWE-bench 65.0%). Виправлення найскладніших дефектів логіки та потокобезпечності.
   - *GPT-OSS 120B:* Альтернативний арбітр масштабних структур даних та міжмодульних протоколів.
   - Формує стандартизований технічний висновок: `[CODE_AUDIT_REPORT]`.

5. **Рівень 5: Фінальний вердикт Antigravity (Golden Standard Orchestrator):**
   - Antigravity читає висновки Code-моделі (`[CODE_AUDIT_REPORT]`).
   - Здійснює системний аудит: запуск компілятора бінарників (Caprica `.pex`, `build_*.py`), сумісність із детерміністичною 1-мс шиною (`proto/telemetry_bus.proto`), навантаження на E/P-ядра процесора, проходження HIL-тестів (`mock_hardware_feeder.py`).
   - Формує підсумковий звіт (Фаза 5, `walkthrough.md`) для користувача з обов'язковим звітом статусів/відповідей усіх провайдерів.
   - Лише після проходження всіх верифікацій та окремого схвалення користувача санкціонує пуш релізу онлайн.

### Обов'язкова видимість інференсу в чаті (Chat-Screen AI Invocation Visibility):

## 6. Протокол безвідмовного доступу до файлів через локальний Git (Git-First Local Access)

1. **Принцип усунення помилок «Permission denied / no access»:**
   - У стандартному режимі пісочниці (`Standard Sandbox` / `BypassSandbox: false`) прямі виклики читання файлів у сторонніх підпроцесах можуть стикатися з ізоляцією.
   - **Локальний Git працює у Standard Sandbox нативно, безшовно і з нульовими запитами дозволів.**
   - Усі операції аналізу коду, читання контексту та підготовки файлів для відправки в моделі виконуються через локальний Git:
     ```bash
     git show HEAD:<шлях_до_файлу>
     git diff <файл>
     git log -n 5 --stat
     git status
     ```
   - Завдяки цьому Python-скрипти раннера отримують вміст файлів через буфер Git без ризику виникнення виключень `PermissionError / no access`.

2. **Стандарт запуску команд (Мінімізація модальних вікон) та Залізний бар'єр перехоплення (Hard Deny Gate & Zero Inline-Eval):**
   - Усі дії виконуються через уніфікований раннер:
     `python3 /home/hills/Documents/.agents/scripts/diagnostic_runner.py ...`
   - Дозволений префікс автосхвалення «Always Allow» захищає від спливаючих вікон.
   - Категорично заборонено використовувати вкладені підстановки `$(...)`, одноразові `curl` та ланцюжки `&&` всередині пісочниці.
   - **Заборона інлайн-виконання коду (`--eval` Purge):** Прапорець `--eval` вилучено з раннера як вразливість. Генерація коду здійснюється виключно в цільові файли через `--synthesize-script` з реєстрацією в сесійному реєстрі провененсу, а виконання — через `--run`.
   - **Системний хук `pre_tool_hook.py`:**
     1. **Zero Inline-Eval Gate (v0.8.2):** Фізично відхиляє (`decision: deny`) будь-які спроби виконання інлайн-скриптів (`python[0-9.]* -c`, `bash -c`, `sh -c`, `eval `, `exec `, `<<EOF`, `diagnostic_runner.py --eval`). Повертає обов'язкову регламентну інструкцію синтезу коду через моделі ШІ.
     2. **Runtime Circuit Breaker Gate (v0.8.2):** Фізично зупиняє ReAct-цикл (`decision: deny`) при фіксації 2 послідовних збоїв виконання скрипта/команди.
     3. **Git Safety Gate:** Фізично відхиляє будь-які спроби несанкціонованого виконання заборонених деструктивних Git-операцій (`git reset`, `git revert`, `git restore`, `git push`, `git merge`, `git rebase`).

3. **Централізований хаб управління `Antigravity_Mgr` та Multi-Project Symlink Mesh (v0.8.2):**
   - Усі системні артефакти, звіти та модульні інструменти 5-фазного циклу консолідуються в єдиній директорії:
     `/home/hills/Documents/Antigravity_Mgr/`
   - **Модульний Toolbelt (`Antigravity_Mgr/tools/`):**
     - `phase1_inspect.py` — нативна інспекція складних форматів (`--docx`, `--xml`, `--json`, `--ast`) без запуску інтерпретатора.
     - `phase2_router.py` — валідатор структури планів та розрахунок маршруту моделі (Ollama vs Groq LPU).
     - `phase4_provenance.py` — сесійний реєстр SHA256 хешів (`/tmp/antigravity_provenance_ledger.json`) та Anti-Shadow Gate.
     - `phase5_verify.py` — комплексна верифікація робочого простору та збір метрик.
   - **Мережа символьних посилань (Symlink Mesh):**
     - Зворотна сумісність: `.agents/tools` $\to$ `Antigravity_Mgr/tools`, `.agents/artifacts` $\to$ `Antigravity_Mgr/artifacts`.
     - Доменні оверлеї: `fallaut/Antigravity_Mgr` $\to$ `../Antigravity_Mgr`.
     - Глобальна змінна: `ANTIGRAVITY_MGR_PATH="/home/hills/Documents/Antigravity_Mgr"` у `.env`.

4. **Протокол прямого виконання на хості (Host-First Execution Protocol v0.8.3):**
   - **Скасування правила «Try sandboxed first» для хостових підсистем:**  
     Оскільки Linux-пісочниця через ізоляцію `Network Namespace` фізично блокує loopback-доступ до локальної Ollama (`127.0.0.1:11434`), а також монтує каталог `.git` як Read-Only, намагатися запускати ці операції у пісочниці категорично заборонено (це провокує помилки `Connection refused`, збої Git та недоброчесний обхід регламенту).
   - **Обов'язковий режим `BypassSandbox: true`:**  
     Для команд системного раннера `diagnostic_runner.py`, модулів `Antigravity_Mgr/tools/`, операцій локального Git (`git add`, `git commit`), скриптів компіляції Caprica/Wine та системних сповіщень `aplay` агент зобов'язаний одразу і першим вибором використовувати `BypassSandbox: true`.
   - **Автосхвалення в `pre_tool_hook.py` (Always-Allow без модальних вікон):**  
     Хук `pre_tool_hook.py` містить довірений білий список префіксів цих хостових інструментів і санкціонує їх автоматично (`decision: allow`) без генерування спливаючих запитів користувачу.
